# 실제 캡쳐 기반 NLP/시그널 추론 학습 트랙 — 설계

**날짜:** 2026-06-10
**상태:** 설계 확정 (구현 계획 대기)
**목적:** 상용화가 아닌 **개인 학습**. 실제 데이팅 대화 캡쳐(마스킹)를 SignalMate 엔진에 흘려보내며, "개념은 알지만 실전이 약한" 상태를 "왜 맞고 틀리는지 손으로 아는" 상태로 끌어올린다.

## 배경

SignalMate에는 이미 완성된 분석 파이프라인이 있다:
OCR(vision) → 룰 기반 시그널(`pattern-matcher`) → 임베딩/유사도 검색(`embeddings/`) → LLM 시그널 보정(`chains/signal-enhancer`) → 추천 생성(`chains/recommendation-generator`) → 평가(`evaluation/comparator`, `metrics`).

이 파이프라인을 **학습용 엔진**으로 재사용한다. 새 기능을 만드는 게 목적이 아니라, 기존 엔진을 실제 데이터로 관찰·실험·튜닝하는 게 목적이다.

## 학습자 프로필

- NLP/ML 개념(임베딩·LLM·프롬프트·분류)은 안다. 직접 분석/실험해본 경험은 적다.
- 결과물 형태: **해부 → 실험노트 → 개선루프** 3단계를 순차적으로 쌓아올리는 커리큘럼.

## 구조 결정: C 하이브리드

기존 파이프라인을 그대로 "엔진"으로 쓰되, 학습 산출물은 별도 `learning/` 공간에 둔다. 실제 코드를 만지는 실전 감각 + 일지의 회고성을 모두 챙기고, 프로덕션 코드는 더럽히지 않는다.

검토했으나 선택하지 않은 대안:
- **A. 코드 내장형** — 학습 코드를 `lib/ai`에 직접 붙임. 진입 무겁고 코드가 지저분해짐.
- **B. 저널 중심형** — markdown 일지 위주, 코드 거의 안 건드림. 실전 감각이 덜 붙음.

## 작업 공간

엔진(`lib/ai`)이 `landing-page-nextjs` 안에 있으므로 학습 공간도 거기에 둬서 엔진 모듈을 직접 import한다.

```
landing-page-nextjs/learning/
  README.md            # 학습 트랙 안내 (나중의 나를 위한)
  captures/            # ① 마스킹된 실제 캡쳐 = 데이터셋  (.gitignore)
    0001.json          #   {id, source, context, messages:[{sender, text}], myLabel?}
  traces/              # Phase 1 산출물: 캡쳐별 단계 추적 노트
  experiments/
    dataset.jsonl      # Phase 2: 캡쳐 + 내 라벨 + 시스템 출력
    cards/             # Phase 2~3: 실험 카드 (가설→변경→결과)
  scripts/
    trace.ts           # 캡쳐 1개를 파이프라인에 흘려 각 단계 입·출력을 덤프
    eval.ts            # 데이터셋 전체에 대해 시스템 vs 내 라벨 비교
```

### 캡쳐 등록 규칙 (서있는 원칙)

1. 캡쳐는 텍스트로 옮겨 `captures/NNNN.json`에 저장. 이미지 원본은 저장하지 않는다.
2. **마스킹 = 삭제가 아니라 일반화(generalization)** — 실명·지명·직장·연락처·SNS 핸들을 통째로 지우면 분석 가치(사회적 맥락)도 함께 사라진다. 대신 식별성은 없애고 **사회적 인식 범주만 남긴다.**
   - 본문(`messages`)에선 식별어를 인라인 토큰으로 치환: `[직장]`, `[지명]`, `[학교]` 등. 말투·문장 구조·이모지·길이·답장 텀은 보존(분석 가치가 여기 있다).
   - `context` 블록에 그 토큰이 **한국 사회에서 갖는 인식 범주**를 한 번만 일반화해 기록. 예: "삼성전자 마케팅" → `job: "대기업 / 사무직"`, "강남 거주" → `residence: "수도권 번화가"`.
   - **재식별 방지 원칙**: 범주는 여러 사람에게 두루 해당될 만큼 넓게 적는다. "삼성전자 마케팅팀 5년차"처럼 좁히면 다시 식별 가능해지므로 금지.
3. `captures/`는 **`.gitignore`** 처리 — 일반화했어도 제3자(상대방) 데이터라 git에 올리지 않는다. git에는 **집계된 실험 노트만** 커밋한다(개별 대화 원문 X).

**캡쳐 JSON 예시:**

```jsonc
{
  "id": "0001",
  "source": "데이팅앱 A",
  "context": {                    // 식별정보 → 일반화된 사회적 범주 태그
    "job": "대기업 / 사무직",       // "삼성전자 마케팅" → 이렇게 넓게
    "residence": "수도권 번화가",   // "강남" → 이렇게
    "age_band": "20대 후반"
  },
  "messages": [
    { "sender": "them", "text": "나 [직장] 근처 카페 자주 가ㅋㅋ" },
    { "sender": "me",   "text": "오 거기 어디 좋은 데 있어?" }
  ]
  // myLabel 은 Phase 2에서 추가
}
```

## Phase 1 — 해부 (파이프라인 추적)

**목표:** 마스킹된 캡쳐 하나가 엔진을 통과할 때 각 단계가 무엇을 받아 무엇을 내놓는지 눈으로 보고, "이 시스템이 왜 이렇게 판단하는지" 체득.

**산출물:** 캡쳐별 `traces/NNNN.trace.md` — 각 단계의 입력 → 출력 → "내 눈엔 말이 되나?" 한 줄 코멘트.

**`scripts/trace.ts`가 덤프할 단계들** (기존 엔진 모듈 그대로):

| 단계 | 모듈 | 보는 것 | 붙는 개념 |
|---|---|---|---|
| 1. 파싱/정규화 | 텍스트 직접 입력 → messages (OCR 건너뜀) | 원문이 발화 단위로 어떻게 쪼개지는가 | 토큰화·정규화, 화자 분리 |
| 2. 룰 시그널 | `agent/tools/pattern-matcher.ts` | warm_tone, emoji_engagement, emoji_drop 등 어떤 피처가 켜졌나 | 규칙 기반 피처 추출 |
| 3. 임베딩/유사검색 | `embeddings/embed-conversation.ts`, `similarity-search.ts` | 이 대화의 벡터, 가장 가까운 이웃 대화 | 임베딩, 코사인 유사도, 의미의 벡터화 |
| 4. LLM 시그널 보정 | `chains/signal-enhancer.ts` | 룰 시그널이 LLM 거치며 어떻게 바뀌나 | 프롬프트 구조, few-shot, structured output |
| 5. 추천 생성 | `chains/recommendation-generator.ts` | 최종 권유 메시지 | 컨텍스트 주입, 생성 |

**학습 루틴 (캡쳐 3~5개):** 캡쳐 등록 → `trace.ts` 실행 → 단계마다 예상과 같/달랐는지 기록. 특히 3번(임베딩)에서 끌려온 이웃 대화가 실제로 비슷한지 직접 검증.

**얻는 것:** 신호가 어디서 생기는지 지도. 규칙/임베딩/LLM이 각각 더하는 신호를 구분하는 눈.

## Phase 2 — 실험노트 (라벨링 & 오답 분석)

**목표:** 캡쳐를 모아 직접 라벨링하고, 시스템 판단과 내 직관이 어디서 갈리는지 분석.

**산출물:** `experiments/dataset.jsonl` (캡쳐 + 내 라벨 + 시스템 출력) + 불일치 분석 노트.

**흐름:**

1. **라벨 스키마** — 시스템 출력과 비교 가능한 최소 축:
   - `temperature`: 호감 온도 (cold / neutral / warm / hot)
   - `topSignal`: 내가 본 가장 강한 신호 한 줄
   - `nextMove`: 내가 생각하는 다음 액션
2. **블라인드 라벨링** — 시스템 출력을 보기 전에 내 라벨부터 기록. ground truth 개념의 핵심.
3. **시스템 실행 → 나란히 기록** — `eval.ts`가 `내 라벨 | 시스템 출력 | 일치여부` 테이블 생성.
4. **불일치 로그 (핵심)** — 갈린 케이스마다 왜 갈렸는지 가설: 룰이 거칠었나 / 임베딩이 엉뚱한 이웃을 끌어왔나 / LLM 프롬프트의 사각지대인가 / **내 라벨이 틀렸나**.

**붙는 개념:** 데이터셋 구축, 라벨링, ground truth, 오답 분석, 평가자 간 불일치. 기존 `evaluation/comparator.ts`·`metrics.ts`를 여기서 처음 가볍게 사용.

**얻는 것:** "모델이 틀린다"가 손에 잡히는 구체적 케이스 묶음으로 전환. Phase 3의 개선 대상이 여기서 나온다.

## Phase 3 — 개선루프 (측정 → 변경 → 재측정)

**목표:** Phase 2의 불일치에서 하나를 골라 가설을 세우고 딱 한 군데만 바꾼 뒤 eval로 before/after 측정.

**산출물:** `experiments/cards/NNNN.md` — 실험 카드 묶음.

```
실험 카드 #003
- 대상 불일치: warm_tone이 비꼬는 말투를 호감으로 오판 (Phase2 케이스 5,9,12)
- 가설: 룰이 긍정 이모지만 보고 부정 문맥을 못 봄
- 변경(딱 하나): few-shot에 반어법 예시 1개 추가  ← 또는 룰 임계값 / 프롬프트 중 하나만
- 측정: eval.ts → dataset 전체 정확도  (before 0.62 → after 0.71)
- 결론: 효과 있음 / 표본 18개라 과적합 의심 → 캡쳐 더 모아 재검증
```

**규율 (학습의 핵심):**
1. **한 번에 한 변수만** — 룰·프롬프트·few-shot 동시 변경 금지.
2. **항상 같은 데이터셋으로 재측정** — 비교 성립(회귀의 개념).
3. **과적합 경계** — 작은 표본에 과적합될 위험을 *느끼는 것* 자체가 배움.
4. 가설이 틀려도(성능 안 오르거나 떨어져도) 카드에 기록 — 실패한 실험도 데이터.

**붙는 개념:** 회귀 측정, 과적합, 메트릭 선택, 통제 변수 실험, 베이스라인 비교.

**얻는 것:** 프롬프트/룰 변경이 성능을 어떻게 움직이는지 인과 감각.

## 전체 흐름

해부 → 실험노트 → 개선루프. 각 Phase가 다음 Phase의 입력을 만든다: 추적이 라벨링 대상을, 라벨링이 개선 대상을 공급한다.

## 범위 밖 (YAGNI)

- 새 프로덕션 기능, UI 변경 없음.
- **모델 학습/파인튜닝 없음 — "관찰 + 프롬프트/룰 튜닝"에 한정.** 두 종류의 튜닝을 구분한다:
  - **하지 않음 — 파인튜닝(가중치 학습):** 베이스 모델을 내 데이터로 추가 학습시켜 모델 가중치 자체를 바꾸는 것. 라벨 수천~수만 개·학습 인프라가 필요하고, 변경 효과가 불투명한 가중치 변화에 묻혀 인과 추적이 어렵다.
  - **함 — 관찰 + 프롬프트/룰 튜닝(가중치 동결):** 모델 가중치는 얼려둔 채 *내가 읽고 이해할 수 있는* 부분만 조절한다 — 룰 임계값(`pattern-matcher`), 프롬프트 문구(`system-prompt`), few-shot 예시(`few-shot-examples`), 검색 파라미터(top-k 등).
  - **이유:** 학습 목표가 "추론을 *이해*하는 것"이라, 바꾼 내용을 눈으로 읽고 인과를 추적할 수 있는 개입이 교육적이다. 작은 표본에서 파인튜닝은 과적합·교란만 키운다.
  - **영구 금지가 아닌 이번 스코프 결정** — 나중에 파인튜닝 자체를 배우고 싶으면 별도 트랙으로 분리한다.
- 대규모 데이터셋 없음 — 수십 개 규모의 개인 캡쳐로 충분(작은 표본의 한계를 느끼는 것도 학습 목표).
