# Situation-First Analysis Design

## 배경

SignalMate의 원래 입력은 채팅 텍스트와 캡처 중심이었다. 하지만 실제 사용 목적은 채팅 신호만 읽는 것이 아니라, 직접 만났을 때의 분위기와 만남 이후 연락 흐름까지 함께 보고 다음 행동을 정하는 것이다.

따라서 제품의 1차 입력 단위를 "채팅 대화"에서 "관계 상황 기록"으로 확장한다. 채팅은 여전히 중요한 근거지만 필수 입력은 아니다. 사용자는 만남 후기 텍스트만으로도 분석을 시작할 수 있어야 한다.

## 목표

- 첫 화면에서 채팅, 캡처, 만남 후기, 이후 연락 흐름, 현재 고민을 모두 받을 수 있게 한다.
- 채팅이 없어도 만남 후기 중심 분석이 가능하게 한다.
- 분석 결과에서 채팅 신호, 실제 만남 신호, 만남 뒤 연락 신호를 구분해 보여준다.
- 신호가 충돌할 때 그 충돌을 명시한다. 예: 채팅은 적극적이지만 만남 뒤 연락은 짧아졌다.
- 다음 행동을 구체적으로 제안한다. 예: 기다리기, 가볍게 안부 보내기, 애프터 제안하기, 정리 고려하기.
- 기존 대화 분석 API와 저장 구조를 가능한 한 재사용하되, 이후 타임라인형 관계 기록으로 확장할 수 있게 둔다.

## 비목표

- 이번 설계에서는 장기 관계 관리 앱 전체를 만들지 않는다.
- 이번 설계에서는 별도 심리 상담, 연애 코칭 콘텐츠, 점수화 게임화를 추가하지 않는다.
- 이번 설계에서는 사용자 개인 식별 정보를 더 수집하지 않는다.
- 이번 설계에서는 캡처 원본 이미지 저장 정책을 바꾸지 않는다.

## 제품 방향

추천 접근은 "통합 입력형"이다.

첫 화면의 의미를 다음처럼 바꾼다.

> 지금 상황을 입력해 주세요.  
> 카톡 캡처, 대화 내용, 실제 만났을 때 느낀 점, 이후 연락 흐름을 함께 분석할게요.

사용자는 아래 입력 중 하나 이상을 제공할 수 있다.

- 채팅 텍스트
- 채팅 캡처
- 실제 만남 후기
- 만남 뒤 연락 흐름
- 지금 고민

입력은 내부적으로 다음 타입 중 하나로 분류한다.

- `chat`: 채팅/캡처 중심
- `meeting_note`: 실제 만남 후기 중심
- `mixed`: 채팅과 만남 후기가 섞인 입력
- `follow_up`: 만남 뒤 연락 흐름 중심

분류는 1차 구현에서는 사용자가 선택하게 하고, 추후 자동 분류로 확장할 수 있다.

## 사용자 흐름

### 1단계: 상황 입력

기존 "대화 내용" 텍스트 영역을 "상황 입력"으로 변경한다. 채팅 메시지 형식이 아니어도 허용한다.

예시 입력:

```text
어제 처음 만났는데 대화는 끊기지 않았고 2시간 정도 같이 있었어.
상대가 질문을 많이 하진 않았지만 웃으면서 들어줬고, 다음에 또 보자는 말은 없었어.
집에 와서 내가 먼저 잘 들어갔냐고 보냈고 답장은 왔는데 짧았어.
이제 내가 또 연락해도 되는지 모르겠어.
```

채팅 캡처 업로드는 유지한다. 캡처에서 추출된 텍스트도 같은 상황 입력에 합쳐진다.

### 2단계: 상황 보강 질문

설문처럼 길게 만들지 않고, 선택형 6개와 자유 입력 1개로 시작한다.

- 관계 단계: 첫 만남 전 / 첫 만남 후 / 두세 번 만남 후 / 식어가는 느낌
- 입력 중심: 채팅 중심 / 만남 후기 중심 / 둘 다 / 만남 뒤 연락 중심
- 실제 만남 분위기: 어색함 / 보통 / 좋음 / 아주 좋음 / 해당 없음
- 상대 적극성: 낮음 / 보통 / 높음 / 잘 모르겠음
- 만남 뒤 연락: 아직 없음 / 내가 먼저 함 / 상대가 먼저 함 / 답장이 느려짐 / 이어지는 중 / 해당 없음
- 지금 원하는 것: 다음 메시지 / 애프터 제안 / 기다릴지 판단 / 정리할지 판단

이 답변들은 `situationContext`에 자연어로 병합한다. 기존 `lib/situation-context-builder.ts`는 이 방향과 맞으므로 확장해서 사용한다.

### 3단계: 분석 결과

결과 화면은 다음 섹션을 갖는다.

- 현재 관계 온도
- 채팅 신호
- 실제 만남 신호
- 만남 뒤 연락 신호
- 신호 충돌 또는 가장 큰 불확실성
- 지금 할 행동
- 보낼 메시지 예시
- 피해야 할 행동

채팅이 없는 경우에는 채팅 신호 섹션을 "입력 없음"으로 표시하고, 만남 후기와 이후 연락 흐름 중심으로 해석한다.

## 데이터 모델

1차 구현은 DB 스키마 변경 없이 진행한다.

기존 `StoredConversation`을 유지한다.

- `rawText`: 사용자가 넣은 원문 상황 입력 전체
- `messages`: 채팅 형식으로 파싱 가능한 메시지가 있을 때만 채운다
- `situationContext`: 보강 질문 답변을 자연어로 병합한 텍스트
- `relationshipStage`: 기존 enum을 유지
- `meetingChannel`: 기존 enum을 유지
- `userGoal`: 기존 enum을 유지

단, 채팅 메시지가 없는 만남 후기 입력도 허용해야 하므로 기존 API의 "메시지 2개 이상" 검증은 입력 타입에 따라 완화한다.

추후 2차 구현에서는 다음 구조를 별도 JSON 또는 테이블로 분리할 수 있다.

```ts
type SituationInput = {
  inputFocus: "chat" | "meeting_note" | "mixed" | "follow_up";
  meetingVibe?: "awkward" | "normal" | "good" | "great" | "none";
  otherInitiative?: "low" | "medium" | "high" | "unknown";
  afterMeetingContact?: "none" | "self_first" | "other_first" | "slower" | "ongoing" | "not_applicable";
  desiredHelp?: "next_message" | "ask_for_date" | "wait_or_send" | "decide_to_stop";
  freeText?: string;
};
```

## 분석 로직

### 규칙 기반 분석

기존 규칙 엔진은 메시지 배열을 전제로 한다. 만남 후기 중심 입력에서는 다음 보완 분기가 필요하다.

- 메시지가 0~1개이고 `situationContext` 또는 `rawText`가 충분하면 `limited_signal` 대신 상황 기반 신호를 만든다.
- 만남 분위기와 이후 연락 흐름을 별도 신호로 만든다.
- 신호 충돌을 감지한다.

초기 규칙 예시:

- `meeting_positive_vibe`: 만남 분위기가 좋음/아주 좋음
- `meeting_low_reciprocity`: 상대 질문, 다음 만남 언급, 이후 연락이 약함
- `post_meeting_followup_positive`: 상대가 먼저 연락하거나 연락이 이어짐
- `post_meeting_followup_caution`: 답장이 짧아졌거나 느려짐
- `signal_conflict`: 채팅/만남/이후 연락 신호가 서로 다른 방향

### LLM 분석

프롬프트는 "채팅 분석"에서 "관계 상황 분석"으로 바뀌어야 한다.

중요한 지침:

- 채팅이 없어도 분석한다.
- 만남 후기의 주관적 느낌은 근거로 쓰되 단정하지 않는다.
- 실제 만남 이후 연락 흐름을 강한 최신 신호로 본다.
- 메시지 예시는 상대에게 부담이 적은 한국어로 제안한다.
- 사용자의 감정 결론을 강요하지 않고 행동 옵션을 제시한다.

## API 변경

1차 구현에서는 기존 `/api/v1/conversations`와 `/api/v1/conversations/:id/analyses/stream`을 유지한다.

변경점:

- `POST /api/v1/conversations`가 `inputFocus`와 상황 보강 답변을 받을 수 있게 한다.
- `rawText`만 있고 `messages`가 없더라도 `inputFocus !== "chat"`이면 conversation 생성을 허용한다.
- `conversationInline`에도 상황 보강 필드를 포함한다.

별도 API는 2차에서 검토한다.

## UI 변경

현재 `components/analysis-experience.tsx`의 2단계 흐름은 유지하되 명칭과 항목을 바꾼다.

- 1단계 제목: "대화 내용" → "지금 상황"
- 1단계 힌트: 채팅뿐 아니라 만남 후기와 이후 연락 흐름을 넣을 수 있다고 안내
- 실시간 확인: 채팅 메시지가 파싱되면 미리보기, 아니면 상황 요약 미리보기
- 2단계에 `입력 중심`, `실제 만남 분위기`, `상대 적극성`, `만남 뒤 연락` 선택지를 추가
- 결과 화면에 "실제 만남 신호"와 "만남 뒤 연락 신호" 그룹을 추가

## 오류 처리

- 입력이 비어 있으면 기존처럼 막는다.
- 채팅 메시지가 2개 미만이어도 만남 후기 텍스트가 충분하면 진행한다.
- 만남 후기 텍스트가 너무 짧으면 보강 질문을 먼저 채우도록 안내한다.
- 캡처 추출 실패 시 직접 상황 텍스트를 입력할 수 있게 한다.

## 테스트 계획

- `buildGuidedSituationContext`가 새 보강 질문을 자연어로 병합하는지 테스트한다.
- 채팅 메시지 없이 `rawText`와 `inputFocus=meeting_note`만으로 conversation 생성이 되는지 API 테스트를 추가한다.
- 기존 채팅 중심 분석이 깨지지 않는지 회귀 테스트한다.
- 규칙 엔진이 만남 후기 중심 입력에서 `meeting_*`, `post_meeting_*`, `signal_conflict` 신호를 생성하는지 테스트한다.
- 분석 화면에서 채팅 파싱 결과가 없어도 다음 단계로 이동할 수 있는지 컴포넌트 테스트를 추가한다.

## 단계별 구현 범위

### 1차

이 구현 계획은 1차 범위와 이미 포함된 최소한의 상황 기반 규칙 신호(`meeting_*`, `post_meeting_*`, `signal_conflict`)까지 포함한다. 사람/관계 단위 타임라인 모델과 학습 CLI의 사후 피드백 입력은 다음 계획에서 다룬다.

- 입력 화면 문구 변경
- `inputFocus`와 만남 후 선택 질문 추가
- `situation-context-builder` 확장
- 채팅 메시지 없는 상황 입력 허용
- LLM 프롬프트를 관계 상황 분석 중심으로 보강
- 결과 화면에 만남/후속 연락 섹션 라벨 추가

### 2차

- 규칙 신호 정교화/확장
- 충돌 감지 고도화
- 학습 CLI 입력 추가

### 3차

- 사람/관계 단위 타임라인 모델 추가
- 채팅 캡처, 만남 후기, 이후 연락 흐름을 시간순으로 누적
- 실제 결과 피드백을 이용한 평가 루프 구축

## 승인 기준

- 사용자가 채팅 없이 만남 후기 텍스트만 입력해도 분석을 시작할 수 있다.
- 사용자가 채팅 캡처와 만남 후기를 함께 넣어도 하나의 상황으로 분석된다.
- 결과가 "채팅 신호"와 "실제 만남/이후 연락 신호"를 구분해 설명한다.
- 다음 행동이 구체적인 메시지 예시와 함께 제공된다.
- 기존 채팅 캡처 분석 흐름은 계속 동작한다.
